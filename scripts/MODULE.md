# Ops Tooling Module Card

- purpose: command-line lifecycle and local developer operations.
- `scripts/type-check.sh` is the repo's mypy gate and the ONE copy of that invocation: `make type-check` runs it in a throwaway `python:3.12-slim` container, and `.github/workflows/ci-cd.yml`'s "Run mypy type checking" step runs it directly. It must stay per-service (`cd services/<svc> && mypy app`, plus `src`/`app.py` for web-ui and the shared `services/*.py` + underscore shims) — a single `mypy services/` pass aborts with `Duplicate module named "app"` and exits 2 before analysing anything, which is what made this gate a no-op from the day it was written until 2026-08-07 (permanently red locally, permanently green in CI behind `|| true`). It pins its own mypy and stub versions; do not let either caller grow its own copy of the command, and do not re-add a result-swallowing suffix. Frozen by `tests/unit/test_type_check_gate.py`.
- product/module functionality: Docker Compose start/stop/logs/status/test, host-AI runtime, provider checks, `configure-provider` (probes real LLM/embedding provider availability and writes a verified choice to `.env` -- SPEC-provider-routing.md R6), Backend Core tab commands, local MCP tab wrappers, init/model setup, cleanup.
- scope boundaries: orchestrates services but does not implement service-domain behavior.
- connected modules/submodules: Docker Compose, AI Engine, Browser Engine, Backend Core, Test Harness, Shared Config.
- allowed change types: CLI parser fixes, token/bootstrap generation, host-AI environment handling, Backend Core ops wrappers, test wrapper additions, docs.
- special operating rules: never print generated service tokens or `BACKEND_AGENT_API_TOKEN`; preserve token-store file permissions (0600) and container-to-host routing behavior. `service_env_with_tokens()` must mint one INDEPENDENT token per scope for all four of `SERVICE_TOKEN_ENVS` (`AI_ENGINE_API_TOKEN`, `BACKEND_CALLBACK_TOKEN`, `BACKEND_AGENT_API_TOKEN`, `BROWSER_ENGINE_API_TOKEN`) — never one shared value, which collapses the four trust scopes (browser-engine accepts only its own token, so a shared value hands the agent principal the scrape/CDP/credential control plane). Values are persisted per scope in `data/service-tokens.json` so they stay stable across restarts; `ensure_service_token()` never overrides an operator-supplied env/`.env` value and seeds `AI_ENGINE_API_TOKEN` only from the legacy single-token `data/host-ai-token` file so existing installs do not rotate silently. Every consumer asks for its own scope: `cmd_host_ai` for AI + callback, `run_backend_tab_tool` for `BACKEND_AGENT_API_TOKEN`. Frozen by `tests/unit/test_cli_host_ai.py::test_service_env_mints_four_distinct_tokens_in_stock_env`. Every command that calls `service_env_with_tokens()` and can (re)create the stack MUST call `load_env_file()` first, so an explicit `.env` value for one of the four token envs (or any other compose-interpolated var) is honored instead of silently falling through to a different value: `cmd_start`, `cmd_host_ai`, `cmd_check_provider`, `cmd_configure_provider`, `cmd_tabs_import`, and `cmd_test` all do this. `cmd_test` was missing it (`load_env_file` was added to the CLI for the other commands but never retrofitted onto the pre-existing `test` command, even after it grew a `docker compose up` for `--type integration`/`--type e2e`); the result was `test --type integration` and `start -d` able to hold the running stack on different tokens for the identical `.env`. Frozen by `tests/unit/test_cli_host_ai.py::test_cmd_test_loads_env_file_like_other_stack_commands`. `host-ai`'s uvicorn is the one bind that runs on the operator's own machine (not in a container), so it is outside the "published ports are loopback-only" invariant (`docker-compose.yml`/`CLAUDE.md`) yet has the same failure mode: its `--host` default must never be `0.0.0.0` (whole-LAN reachable). `resolve_host_ai_bind_host()` resolves the bind address: an explicit `--host` (including `0.0.0.0`, with a printed warning) always wins; left unset it calls `discover_docker_bridge_gateway()`, which finds this checkout's Compose network (matched by the `tab-organizer-network` suffix, since the project-name prefix varies per worktree/clone) and returns its gateway IP via `docker network inspect` — never a hardcoded constant like `172.17.0.1`, which is only the *default* bridge's address and may not be the network these containers use. Containers reach that same address via the per-service `extra_hosts: host.docker.internal:host-gateway` entry, so this keeps `--host-ai` working while nothing outside Docker can reach the host-run AI Engine. Discovery failing (Docker unavailable, network not created yet, or an ambiguous match) raises `SystemExit` with the fix instead of guessing a wide-open default — token auth (`AI_ENGINE_API_TOKEN`) is defense in depth here, not the only control. Covered by `tests/unit/test_cli_host_ai.py` (`test_host_ai_parser_default_host_is_not_bound_to_all_interfaces`, `test_resolve_host_ai_bind_host_*`, `test_discover_docker_bridge_gateway_*`, `test_cmd_host_ai_binds_discovered_gateway_not_wide_open`, `test_cmd_host_ai_fails_closed_when_bridge_undiscoverable`). `AI_PROVIDER`/`EMBEDDING_PROVIDER` have no default anywhere in this file either: `host-ai` and `check-provider` both resolve the provider through `_require_explicit_provider()`, which accepts only an explicit flag or an already-set env var (either one is R3's "record of consent") and otherwise raises `SystemExit` naming `configure-provider` as the fix -- it never invents "claude_code"/"ollama"/"openrouter" the way this file used to. Frozen by `tests/unit/test_cli_host_ai.py::test_cmd_host_ai_fails_closed_when_ai_provider_not_set`, `::test_cmd_host_ai_fails_closed_when_embedding_provider_not_set`, `::test_cmd_host_ai_accepts_explicit_provider_flags`, and `tests/unit/test_cli_check_provider.py` (all four tests).
`configure-provider` never writes `AI_PROVIDER`/`EMBEDDING_PROVIDER` to a route it has not **called**. This sentence used to say "did not verify available", and that was the same false-verification class this repo corrected for `openrouter.supports.embeddings`: for a `type: cloud` provider the probe asked only whether the API-key env var was non-empty, so a stale, revoked, typo'd or wrong-account key was reported as "verified available" and written to `.env` under a menu captioned "only verified-available options shown". Availability is now three states, not a boolean. `verification: configured` means a key or binary is present; `verified` means `verify_llm_route`/`verify_embedding_route` made the cheapest REAL generate/embed call through the actual adapter and it succeeded; `refuted` means the provider answered 401/403/402/400/404 — positive proof the credential or model id is wrong, not merely an absence of proof. A timeout, transport error or 5xx stays `unverified` (offline is not refuted, so the tool still works on a plane). A refuted route is never written; an unverified one is written only on an explicit `--allow-unverified` or an interactive confirmation, and the outcome is recorded in `.env` as `AI_PROVIDER_VERIFIED`/`EMBEDDING_PROVIDER_VERIFIED` so the provenance of the choice survives the write. Every probe verdict passes through `redact_secrets()`, which strips URL userinfo **and** query-string credentials (`?key=...`) — the Gemini adapter authenticates by query parameter and httpx puts the whole URL into `HTTPStatusError`, so the raw message can literally be the key. `probe_llm_provider`/`probe_embedding_provider`/`probe_ollama_installed_models` and the two `verify_*_route` functions are kept as separate module-level functions specifically so tests can mock the probe boundary. It always leaves `EMBEDDING_DIMENSIONS` blank via `scripts/init.py`'s `update_embedding_model_env()` so it resolves from `config/ai_models.yaml` at runtime instead of drifting from `EMBEDDING_MODEL`. Embedding candidates are filtered by TWO catalog checks before they are ever probed -- `is_provider_supported(provider, "embeddings")` and `get_provider_models(provider, "embedding")` -- so a provider that cannot embed can never be offered regardless of what a probe returns. On the live catalog the two checks currently agree on every provider, so a test that only exercises the real catalog cannot tell which one is doing the excluding; `test_supports_embeddings_filter_excludes_provider_even_with_phantom_models` and `test_embedding_models_filter_excludes_provider_even_with_supports_flag_true` each monkeypatch one check to disagree with the other and assert the remaining one still excludes the provider, so deleting either check independently fails its own test. Those tests used `openrouter` as their "cannot embed" example until 2026-08-05, when the catalog entry they leaned on turned out to be false (openrouter does serve embeddings -- see `config/MODULE.md` and `docs/SPEC-provider-routing.md`); the mechanism was never in question, so the example moved to `claude_code`, whose incapacity is structural (no Claude embedding adapter exists in `services/ai-engine/app/providers/`) rather than a catalog opinion about a remote API. `test_the_cannot_embed_example_is_genuinely_incapable` now guards the example itself, because the old one silently stopped being valid and every test kept passing. **Both filters are catalog-derived, and that is what let `configure-provider` self-correct with no code edit when the catalog was fixed -- openrouter became offerable for embeddings automatically.** Never hardcode a provider name into these filters or into the error strings around them. **Every model menu row is rendered through `ai_config.format_model_description()`**, so a listing always shows the provider and cost the model would be used through rather than a bare id — `gpt-5.6-luna` and `openai/gpt-5.6-luna` are otherwise indistinguishable on screen despite being subscription and metered routes to the same weights. Frozen by `tests/unit/test_provider_routing.py::test_configure_provider_menu_rows_are_rendered_with_the_route` (source-level, because the rendering is a call site rather than an observable output of the probe). `host-ai --provider` must offer every provider in `routing.llm_preference_order` and pass through every `--*-command` override (`test_host_ai_parser_offers_every_subscription_cli_provider`, `test_cmd_host_ai_passes_every_subscription_cli_command_override`); host-ai is the only way a subscription CLI is usable at all, so a flag that parses but is never exported leaves the provider unreachable. `tests/unit/test_cli_host_ai.py`'s `_host_ai_args()` builds its Namespace from the real parser rather than a hand-copied dict — the hand-copied one broke every host-ai test with `AttributeError` the first time a flag was added. It reuses `scripts/init.py`'s `.env` read-modify-write helpers and `prompt_choice` rather than duplicating them, and probes CLI/cloud availability via `LLMClient.get_provider_runtime_state()` (same prior art as `check-provider`) but implements its own Ollama `/api/tags` probe independently of `LLMClient`'s private helpers, since `services/ai-engine/app/core/llm_client.py` is a separate, concurrently-changing module (SPEC-provider-routing.md R1/R2/R4). Writes all five keys (`AI_PROVIDER`, `LLM_MODEL`, `EMBEDDING_PROVIDER`, `EMBEDDING_MODEL`, `EMBEDDING_DIMENSIONS`) in one atomic `update_env_vars()` call rather than five sequential read-modify-write passes, so an IO failure partway through cannot leave `.env` with only some of the new selection applied. Frozen by `tests/unit/test_cli_configure_provider.py`.
`scripts/init.py`'s non-interactive path (`main()`, no `--provider` given) refuses the same way rather than defaulting to `ollama`: a piped/CI run with no explicit provider has no record of consent (R3) either. Frozen by `tests/unit/test_init_script.py::test_main_refuses_to_auto_select_provider_when_noninteractive`.
`scripts/mcp/tabs.py` (the local MCP tab wrappers, also the module `cmd_tabs_import`/`cmd_tabs_open` dispatch through) does NOT define its own `DEFAULT_CDP_URL` -- it did until 2026-08-06, and that copy ("http://localhost:9222") diverged from the correct default in `services/browser-engine/app/tabs/cdp.py` ("http://host.docker.internal:9222"), which is what actually resolves to the host from inside the Browser Engine container. `scripts/cli.py`'s `tabs import`/`tabs open` parsers used the wrapper-side constant as their argparse `--cdp-url` default, so the CLI always sent an explicit (wrong) `cdp_url`, which always overrode Backend Core's own correct default -- `tabs import` with no `--cdp-url` failed 100% of the time (`502` from Browser Engine, because `localhost:9222` inside that container has nothing listening on it). The fix: `tab_import_from_browser`/`tab_open` take `cdp_url: str | None = None` and omit the key from the payload when it's `None` (`_optional_non_empty`, which still rejects an explicitly-passed empty/blank string via `_require_non_empty`); `scripts/cli.py`'s two `--cdp-url` argparse defaults are `None` too. This makes Backend Core's `TabImportRequest`/`TabOpenRequest` defaults (`services/backend-core/app/main.py`, already correctly mirroring Browser Engine's constant) the single source of truth whenever the operator or an agent doesn't pass `--cdp-url`/`cdp_url` explicitly -- do not reintroduce a CLI/MCP-side default that restates that value; if a caller here ever needs the literal default, it must import it from `services/browser-engine/app/tabs/cdp.py`, not redeclare it. Frozen by `tests/unit/test_cli_host_ai.py::test_tab_import_from_browser_omits_cdp_url_when_not_provided`, `::test_tab_open_omits_cdp_url_when_not_provided`, and the paired `_passes_explicit_cdp_url_unchanged`/`_rejects_explicit_empty_cdp_url`/`test_tabs_cli_import_and_open_default_cdp_url_to_none` tests -- all assert on the constructed payload/parsed args, not on the function's default-argument value, since the latter would keep passing even if payload construction re-inserted a hardcoded URL.
