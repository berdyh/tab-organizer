# Ops Tooling Module Card

- purpose: command-line lifecycle and local developer operations.
- product/module functionality: Docker Compose start/stop/logs/status/test, host-AI runtime, provider checks, Backend Core tab commands, local MCP tab wrappers, init/model setup, cleanup.
- scope boundaries: orchestrates services but does not implement service-domain behavior.
- connected modules/submodules: Docker Compose, AI Engine, Browser Engine, Backend Core, Test Harness, Shared Config.
- allowed change types: CLI parser fixes, token/bootstrap generation, host-AI environment handling, Backend Core ops wrappers, test wrapper additions, docs.
- special operating rules: never print generated service tokens or `BACKEND_AGENT_API_TOKEN`; preserve token-store file permissions (0600) and container-to-host routing behavior. `service_env_with_tokens()` must mint one INDEPENDENT token per scope for all four of `SERVICE_TOKEN_ENVS` (`AI_ENGINE_API_TOKEN`, `BACKEND_CALLBACK_TOKEN`, `BACKEND_AGENT_API_TOKEN`, `BROWSER_ENGINE_API_TOKEN`) — never one shared value, which collapses the four trust scopes (browser-engine accepts only its own token, so a shared value hands the agent principal the scrape/CDP/credential control plane). Values are persisted per scope in `data/service-tokens.json` so they stay stable across restarts; `ensure_service_token()` never overrides an operator-supplied env/`.env` value and seeds `AI_ENGINE_API_TOKEN` only from the legacy single-token `data/host-ai-token` file so existing installs do not rotate silently. Every consumer asks for its own scope: `cmd_host_ai` for AI + callback, `run_backend_tab_tool` for `BACKEND_AGENT_API_TOKEN`. Frozen by `tests/unit/test_cli_host_ai.py::test_service_env_mints_four_distinct_tokens_in_stock_env`. `host-ai`'s uvicorn is the one bind that runs on the operator's own machine (not in a container), so it is outside the "published ports are loopback-only" invariant (`docker-compose.yml`/`CLAUDE.md`) yet has the same failure mode: its `--host` default must never be `0.0.0.0` (whole-LAN reachable). `resolve_host_ai_bind_host()` resolves the bind address: an explicit `--host` (including `0.0.0.0`, with a printed warning) always wins; left unset it calls `discover_docker_bridge_gateway()`, which finds this checkout's Compose network (matched by the `tab-organizer-network` suffix, since the project-name prefix varies per worktree/clone) and returns its gateway IP via `docker network inspect` — never a hardcoded constant like `172.17.0.1`, which is only the *default* bridge's address and may not be the network these containers use. Containers reach that same address via the per-service `extra_hosts: host.docker.internal:host-gateway` entry, so this keeps `--host-ai` working while nothing outside Docker can reach the host-run AI Engine. Discovery failing (Docker unavailable, network not created yet, or an ambiguous match) raises `SystemExit` with the fix instead of guessing a wide-open default — token auth (`AI_ENGINE_API_TOKEN`) is defense in depth here, not the only control. Covered by `tests/unit/test_cli_host_ai.py` (`test_host_ai_parser_default_host_is_not_bound_to_all_interfaces`, `test_resolve_host_ai_bind_host_*`, `test_discover_docker_bridge_gateway_*`, `test_cmd_host_ai_binds_discovered_gateway_not_wide_open`, `test_cmd_host_ai_fails_closed_when_bridge_undiscoverable`).
- current stubs/placeholders: performance/load test wrapper is not part of `scripts/cli.py test` today; Textual TUI, rofi/fzf quick-pick, and a full MCP SDK server are isolate-for-later.
- irrelevant or incomplete code to remove/rework: outdated comments or test wrappers that point at old absolute paths.
