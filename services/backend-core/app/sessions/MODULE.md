# Backend Sessions Submodule Card

- purpose: session lifecycle and persisted tab-processing state.
- product/module functionality: create/list/delete sessions, current session state, URL records, tab import job records, SQLite FTS search rows, clusters, callback metadata, the idempotent ingest ledger (`ingest_captures`).
- scope boundaries: owns backend session data model and keyword search metadata; URL normalization belongs in `url_input`, semantic vectors and chunked content belong in AI Engine.
- connected modules/submodules: Backend API (ingest endpoint), URL input, Browser callbacks, export, Test Harness persistence tests.
- allowed change types: persistence fixes, migration-safe schema additions, status bookkeeping, focused tests.
- special operating rules: keep file-backed SQLite behavior and in-memory fallback behavior equivalent where tests require it (asserted by `tests/unit/test_ingest_v1.py::test_in_memory_and_sqlite_parity`, which now also compares duplicate-outcome forward docs and `capture_index_counts`); keep FTS queries parameterized. `ingest_scrape_result(IngestCapture) -> IngestOutcome` is the single idempotent writer, entirely under the `RLock`: (1) known `capture_id` → `duplicate` (no state change; an applied row still `pending`/`failed` and STILL the latest applied re-schedules its forward — retry-heals); (2) capture whose `capture_order_key` is below the max over *applied* captures for `(session_id, normalized)` → `stale`, url_record untouched; (3) apply = ledger row + `url_records` + FTS row in ONE SQLite transaction (closes the crash window between "applied" and "recorded"). ORDERING KEY: the module-level `capture_order_key(fetched_at, attempt) = (source_rank, parsed-UTC fetched_at, attempt)` is the ONE total order used everywhere — no lexicographic compare survives (both the stale check and `_latest_applied_lookup`'s `max()` use it; the SQL dropped its `ORDER BY fetched_at`). `source_rank` is derived from `attempt` (legacy shim writes `attempt=0` → rank 0; v1 enforces `attempt>=1` → rank 1), so a legacy capture loses to every v1 capture regardless of clock. `_parse_datetime_utc` normalizes tz-aware to UTC-naive and maps unparseable/garbage to `datetime.min` (garbage ranks BELOW every real capture — the "zzz pins forever" poison inverts into "zzz loses forever"). CLOCK ASSUMPTION: comparability is now ENFORCED, not assumed — `IngestResultV1.fetched_at` is validated + normalized to canonical UTC-naive microsecond ISO at the boundary (422 on garbage); pre-normalization/legacy rows still compare correctly because the key is parse-based. CROSS-PROCESS ATOMICITY: the SQLite path runs `BEGIN IMMEDIATE` as the first statement inside `with self._connect()`, acquiring the write lock BEFORE the duplicate/ordering reads, so the whole check-then-write is serialized even across two `SessionManager` instances on one DB (the `RLock` only guards in-process memory state; contention is bounded by `busy_timeout=5000` → `OperationalError` → 500 → browser-engine retry). SNAPSHOT ROLLBACK: `_ingest_apply` deep-copies the url_record + `session.updated_at` before mutating and restores them if the SQLite writes raise, so a failed ingest leaves memory AND DB at the pre-call state (SQLite rolls back at the `with`-exit); a successful return means both are updated (all under the `RLock`, no reader sees the intermediate). DUPLICATE REPLAY reads ONLY `capture_id` from the incoming request; session/normalized/auth_used/content all come from the STORED ledger row + record via `build_forward_document` (a mutated redelivery can never overwrite or forward the wrong body; a key mismatch logs `ingest.duplicate_key_mismatch`). `capture_index_counts` reports only the LATEST applied capture per `normalized` (attempt-1-failed then attempt-2-indexed reports 0 failures). In-memory keyword search filters EXACTLY like the FTS insertion condition (scraped-only, non-empty title/content, haystack = title+content only — URL/domain are UNINDEXED there too). SQLite path queries/inserts `ingest_captures` directly under the lock (NOT load-all-into-dicts + DELETE-all-reinsert; the ledger is append/update-only); in-memory path uses `self._captures` + `self._latest_applied` dicts. `auth_used` GAP: only the credential-store path sets it true; ambient auth (browser-context cookies, session reuse, auth-wall pages) is invisible → `auth_used=false` there is a known under-report. This layer only guarantees the flag propagates capture → ledger (`auth_used` column) → `/index` document metadata; the decision-37 `auth_used ⇒ local embeddings` gate is a separate work item.
- current stubs/placeholders: tab import jobs are durable status records but do not support cancellation/resume. Durable index-forward outbox: the `ingest_captures` ledger IS the outbox; `list_unforwarded_captures` + `reconcile_pending_forwards` sweep it opportunistically (end of each applied/duplicate ingest, session-scoped pending-only) and at backend-core startup (all sessions, pending+failed), re-forwarding orphans (crash between commit and forward) and marking non-latest rows `superseded`. HONEST LIMITATION: the per-`(session,normalized)` forward lock is in-process only; a hypothetical multi-worker deploy could double-forward a row, but ai-engine `/index` upserts by document id so the cost is duplicate work, never a stale vector — current deployment is single-process and no cross-process lock is added.
- irrelevant or incomplete code to remove/rework: legacy timestamp usage emits deprecation warnings and can be modernized separately.
- docs that must stay aligned: Backend Core card, Backend API card, and `docs/TESTING.md`.
- local validation commands/checks: `make test-backend`; focused files `tests/unit/test_session_persistence.py`, `tests/unit/test_ingest_v1.py`, and `tests/unit/test_backend_tab_workflows.py`.
