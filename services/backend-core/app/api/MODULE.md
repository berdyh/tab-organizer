# Backend API Submodule Card

- purpose: FastAPI route wiring and public backend HTTP contract.
- product/module functionality: health, session CRUD, URL input, tab import/open/search, scrape start, versioned idempotent ingest (`ingest.py`), legacy callback shim, clustering proxy, auth proxy, export, platform route mounting.
- scope boundaries: route definitions and dependency wiring only; domain persistence belongs in `sessions`, `url_input`, `export`, and `platform`.
- connected modules/submodules: Backend platform/session/url/export submodules, AI Engine, Browser Engine, Web UI API client, Ops CLI/MCP tools.
- allowed change types: split routers, move request models beside route groups, add dependency helpers, tighten validation.
- `POST /api/v1/chat` (proxy to AI Engine `/chat`, WI0 B7) requires `Depends(_require_backend_agent_auth)` like `/search` and the agent tab routes -- it was shipped unauthenticated in the first WI0 pass (any LAN client on :8080 could spend provider quota), fixed in the wk0 adversarial-review round. Known follow-up gap (not fixed here): `services/web-ui/src/api/client.py`'s `chat()` sends no bearer token and `docker-compose.yml`'s `web-ui` service is not granted `BACKEND_AGENT_API_TOKEN`, so the Streamlit chat page will now 401 until that wiring lands.
- `GET /api/v1/auth/pending` and `POST /api/v1/auth/credentials` (proxies to Browser Engine's auth queue) require `Depends(_require_backend_agent_auth)` (C3). They shipped unauthenticated while attaching the privileged Browser Engine service token server-side — a confused deputy letting any unauthenticated caller on :8080 read the pending-auth queue and plant credentials for an arbitrary domain. Known follow-up gap (owned by the Web UI batch, not fixed here): `services/web-ui/src/api/client.py`'s `get_pending_auth()`/`submit_credentials()` send no bearer token and `docker-compose.yml`'s `web-ui` service is not granted `BACKEND_AGENT_API_TOKEN`, so those Streamlit flows 401 until that wiring lands (same gap as `chat()` above).
- `_browser_engine_headers()` is the SINGLE outbound token-header builder for the six backend→browser call sites (all reached through `_browser_engine_request_headers()`: scrape dispatch, tab import, tab open, scrape status, auth pending, auth credentials). It sends `BROWSER_ENGINE_API_TOKEN` and nothing else, matching browser-engine's accept side exactly; a callback/AI fallback here could never authenticate and would only disguise a missing-token misconfiguration as an auth bug.
- special operating rules: preserve `/api/v1` paths and current JSON shapes; do not weaken callback bearer auth, the `BACKEND_AGENT_API_TOKEN` checks on agent tab / chat / auth-proxy routes, or the browser-token-only outbound header. `POST /api/v1/ingest/v1` (submodule `ingest.py`, included from `routes.py` which stays the aggregator) is the single versioned idempotent ingest endpoint: `IngestResultV1` (capture_id, attempt>=1, session_id, url, status, content, metadata, auth_used, fetched_at), bearer `BACKEND_CALLBACK_TOKEN` via the shared callback auth. `fetched_at` is validated at the boundary — an unparseable timestamp is a `422` (not a silently-poisoning ledger row), a parseable one is normalized to canonical UTC-naive microsecond ISO. It returns `200 applied`/`200 ignored{duplicate_capture_id|stale_capture}`/`404 session`/`409 url-not-registered`/`422` — replay/stale is a 200 (the writer did nothing wrong; the receiver owns dedupe), NEVER a 4xx browser-engine would miscount as a callback failure. The duplicate response gains an additive `"index"` field summarizing the STORED capture's ledger state (`capture_id` is likewise the stored id) — a summary, never an echo of the input. Registration stays the dispatcher's job (B3): ingest 409s an unregistered url rather than auto-registering, so a token holder cannot inject arbitrary urls. Backend is the SINGLE ai-engine `/index` writer: applied success captures forward asynchronously (`forward_capture_index`, per-`(session,url)` lock + latest-applied re-check → `superseded` skip + a post-lock ledger-state re-check so a racing sweep/re-forward never double-POSTs a settled row). DURABLE FORWARD: the `ingest_captures` ledger is the outbox; `reconcile_pending_forwards` re-forwards orphaned/failed rows — opportunistically at the end of each applied/duplicate ingest (session-scoped, pending-only, excluding the just-scheduled row) and once at backend-core startup (`lifespan` fire-and-forget task, all sessions, pending+failed, never blocks/fails startup). `GET /scrape/status/{id}` overlays ledger `ai_index_failed`/`ai_index_pending`/`downstream_errors` (latest applied per url only) onto the browser payload (merge, never replace). `POST /api/v1/callback/scrape-complete` is a deprecated thin adapter over the same ingest path (`attempt=0`, synthetic capture_id, receipt-time `fetched_at`, unchanged legacy response shape, logs `ingest.legacy_callback_deprecated`); legacy is its OWN ordering tier and loses to EVERY v1 capture unconditionally (receipt-time orders legacy-vs-legacy only).
- current stubs/placeholders: scrape trigger errors are currently not persisted as a durable backend status; tab import jobs have status polling but no cancellation route.
- irrelevant or incomplete code to remove/rework: mixed route groups should be split into focused router modules without changing URLs.
- docs that must stay aligned: Backend Core card, Backend Sessions card, Web UI API card, `docs/ARCHITECTURE_PLAN.md`, `docs/TESTING.md`.
- local validation commands/checks: `make test-backend`; focused files `tests/unit/test_backend_tab_workflows.py`, `tests/unit/test_ingest_v1.py`; integration smoke for route changes.
