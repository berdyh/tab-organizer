# Browser Engine Module Card

- purpose: scrape public/authenticated pages and attach to local browser tabs for import/open workflows.
- product/module functionality: scrape API, CDP tab import/open API, auth detection, auth queue, HTTP/browser scraping, per-result delivery to the backend ingest endpoint.
- scope boundaries: owns scraping and extraction runtime; does not own backend persistence or AI indexing internals. Browser-engine NEVER writes vectors — it POSTs each result to backend `POST /api/v1/ingest/v1` and backend-core is the sole ai-engine `/index` writer.
- connected modules/submodules: Backend Core ingest/callback + tab APIs, Web UI scraping page, Ops CLI/MCP tools, Test Harness.
- allowed change types: scraper lifecycle fixes, auth detection, callback/error contract work, route split/refactor, tests.
- special operating rules: preserve bearer auth on control/auth endpoints, local-only CDP attach, default rejection of private/local scrape targets, batch-local scraper instances, browser launch lock, Playwright shutdown in `finally`, callback token headers, and downstream error reporting. Security note (CHANGED -- the cross-scope ACCEPT fallback was REMOVED): `_browser_engine_token()` reads `BROWSER_ENGINE_API_TOKEN` and nothing else; the old `BACKEND_CALLBACK_TOKEN` then `AI_ENGINE_API_TOKEN` fallback is gone, and an unset value fails CLOSED (401 telling the operator to run `scripts/cli.py start`), never open. The previous card called that fallback an accepted blast-radius tradeoff; it was worse than a tradeoff, because `scripts/cli.py` minted ONE value for all four scopes in every stock deployment -- `BACKEND_AGENT_API_TOKEN` *was* the value this service accepted, so an agent principal opened the entire credential + CDP control plane (verified by execution: the agent token alone returned 200 on `/auth/pending`, `/auth/expire`, `/scrape`, `/detect-auth` and passed auth on `/auth/credentials` and `/tabs/import`). The CLI now mints four independent tokens (`data/service-tokens.json`) and backend-core sends `BROWSER_ENGINE_API_TOKEN` on all six of its browser calls. Do not reintroduce a cross-scope accept fallback; frozen by `tests/security/test_token_scopes.py` (`browser_auth_pending` door) and `tests/unit/test_browser_engine_callbacks.py::test_browser_engine_auth_requires_browser_scope_token`. This applies to the ACCEPT side only -- `_service_token_headers("BACKEND_CALLBACK_TOKEN", "AI_ENGINE_API_TOKEN")` chooses which token to SEND downstream and deliberately keeps its fallback. `validate_cdp_url` keeps the local-host allowlist for CDP *input*, but Chrome's debug port rejects any Host header that is not an IP/`localhost`, so `resolve_cdp_connect_url` resolves the input host (notably `host.docker.internal`) to its IP before Playwright connects; connect failures raise `CDPConnectionError` with an actionable `{code, cause, fix}` message (WI0 B2). Each scrape result is delivered to backend `POST /api/v1/ingest/v1` with a fresh `capture_id` (uuid4 per fetch attempt), a per-`(session,url)` in-process `attempt` counter (`_next_ingest_attempt`; resets to 1 across restarts by design — backend keys ordering on `(fetched_at, attempt)`), `fetched_at` (result.scraped_at ISO), and `auth_used`. A 200-`ignored` (duplicate/stale) is a SUCCESSFUL delivery, not a failure — only transport/4xx/5xx errors increment `backend_callback_failed` (one document per ingest, so `_record_downstream_error` no longer carries batch `docs_affected`/`scope`). AI-index failures now live in the backend ledger and surface via backend `/scrape/status`, not here; browser-engine emits no `ai_index` errors. Structured logging goes through shared `services/observability.py`: `RequestIDMiddleware` binds/echoes `X-Request-ID`; the detached `scrape_urls_background` task receives the request id explicitly and must forward it on the ingest call (merged after the auth headers). Log per-callback failures and auth-queue transitions via `log_event`, never credentials or page bodies (domains/lengths only). `app/main.py`'s `lifespan` calls `config.config_loader.get_ai_config().validate_config()` and refuses to start on a malformed catalog (finding 27) — Browser Engine does not otherwise read this config, but ships and validates the same file AI Engine depends on; `Dockerfile`/`requirements.txt` now copy `config/` and pin `PyYAML` to support this. Browser origins are an allowlist, never `*`: `app/main.py` resolves `allow_origins` through shared `services/cors.py` (`CORS_ALLOWED_ORIGINS`, default the Web UI on :8089) and sets `allow_credentials=False`. Web UI calls this service server-side with `requests`, so it has no legitimate browser-side caller; the old `allow_origins=["*"]` + `allow_credentials=True` let any page the user had open read its responses. The Dockerfile copies `services/cors.py` — keep that in sync. Frozen by `tests/security/test_cors_policy.py` (SEC-43).
- current stubs/placeholders: callback failures are best-effort and must remain visible in batch status; private-network scraping is an explicit local opt-in via `SCRAPE_ALLOW_PRIVATE_NETWORKS`; managed browser launch/profile lifecycle is deferred; CDP attach from a container needs Chrome's debug port bridged to the Docker bridge interface (the default 127.0.0.1 bind is unreachable, and headed Chrome ignores `--remote-debugging-address` so it stays on loopback) — the interim path is a host-side `socat TCP-LISTEN:9222,fork,bind=172.17.0.1 TCP:127.0.0.1:9222` bridge (172.17.0.1 is the default docker0 bridge IP; confirm yours with `docker network inspect bridge`, and do NOT bind `0.0.0.0`, which LAN-exposes the unauthenticated debug port), documented in `docs/archive/2026-07-24-MANUAL_SETUP.md`; host-side tab capture (TS migration, plan decision 24) is the durable replacement. **Open bug, `ScrapeEngine.scrape_batch`** (found 2026-08-07 by the first run of `make type-check` that ever analysed this file): `asyncio.gather(..., return_exceptions=True)` yields `BaseException`, but the conversion loop tests `isinstance(result, Exception)`, so a *cancelled* child task falls through the `else` and is appended to `final_results` as if it were a `ScrapeResult` — every later consumer then attribute-errors on it. Left unfixed on purpose: widening the isinstance changes what a cancellation does to a batch. Marked at the site with the only `# type: ignore`-equivalent (`cast`) in this service.
- **The CDP attach leg HAS now been executed end to end (2026-08-06), closing wk0 gap G2.** `tab_import_jobs` had sat at 0 since the feature was written. A run against a host Chrome with three known tabs completed `total: 3, imported: 3, indexed: 3, failed: 0, errors: []`, and all three came back from `POST /api/v1/search` in `hybrid` mode — two of them on vector similarity alone (0.476, 0.459) against a query sharing no keywords with them, which is what distinguishes real embeddings from an `indexed` counter. Reproducing it needs three things lined up at once: a Chrome started with `--remote-debugging-port=9222`, the socat bridge below, and the firewall rule below. `cli.py tabs import` no longer needs `--cdp-url` (fixed in `4f7b6e4`); before that fix its default could never work.
- **The socat bridge is not sufficient on a machine with a host firewall, and the failure gives you nothing to go on.** Verified 2026-08-06 on Arch with `ufw` active: the listener is bound, `host.docker.internal` resolves to `172.17.0.1`, the container's default route points at it, and the *host* can fetch `/json/version` — but every container connection fails, because ufw's INPUT chain drops docker0 → host traffic. The container sees a bare connection failure with no diagnostic, which reads like a code bug and is not one. This is a plausible reason `tab_import_jobs` has sat at 0: anyone following the recipe above on a firewalled Linux box hits a dead end that looks like broken software. The opening is `sudo ufw allow from 172.16.0.0/12 to 172.17.0.1 port 9222 proto tcp` (firewalld: the equivalent rich rule) — Docker's RFC1918 block only, bridge address only, port 9222 only. **The source range must not be narrowed to `172.17.0.0/16`.** That is the *default* bridge; this compose project gets its own user-defined network (observed 2026-08-06 as `main_tab-organizer-network`, `172.20.0.0/16`), so browser-engine's packets arrive from `172.20.x` and a rule scoped to the default bridge drops them while everything else still looks correct — `host.docker.internal` resolves to `172.17.0.1`, socat is bound, the host can fetch `/json/version`, and a throwaway `docker run` container succeeds *because it lands on the default bridge*. That last point makes this trap self-concealing: the obvious way to test the rule passes while the application fails. Verify from the real service (`docker exec tab-organizer-browser`), never from an ad-hoc container. Compose subnets are also assigned dynamically — four stale ones from other worktrees existed on this machine — so pin `ipam.config.subnet` in `docker-compose.yml` if you want a narrower rule to keep working. Grant it deliberately and revoke it afterwards: **CDP has no authentication, so while that rule stands every container on the bridge has full control of that Chrome.** Never widen it to `0.0.0.0` or to the LAN.
- **A raw HTTP client cannot stand in for browser-engine when testing that bridge.** `curl http://host.docker.internal:9222/json/version` from a container returns `Host header is specified and is not an IP address or localhost` — Chrome's debug server rejects any Host header that is not an IP or the literal `localhost`. That is why `cdp.py` resolves the hostname to an address before connecting, and why a test that curls the hostname form "fails" while the real code path succeeds. Test with the resolved IP (`http://172.17.0.1:9222`), which is what the service actually sends.
