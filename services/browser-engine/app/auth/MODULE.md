# Browser Auth Submodule Card

- purpose: detect authentication requirements and manage credential requests.
- product/module functionality: URL/response/HTML auth detection, pending auth queue, credential handoff.
- scope boundaries: owns auth classification and queue state; does not own credential storage UX or backend sessions.
- connected modules/submodules: Browser scraper, Browser routes, Web UI scraping page.
- allowed change types: detection heuristic fixes, queue behavior, credential validation, tests.
- special operating rules: do not log credentials; callback errors are best-effort unless the contract changes; the credential store is fail-closed — it never invents a throwaway key, and `store()` raises `CredentialStoreError` ({code, cause, fix}) when no key resolves. Callers (`/auth/credentials`) must surface that as a 503, not crash. **Key resolution as actually shipped (verified against code, not aspirational):** `queue.py`'s `_resolve_fernet()` tries an explicit arg, then `_load_key_from_keyring()`, then `CREDENTIAL_ENCRYPTION_KEY`. The keyring step is DORMANT in every built container — `keyring` is not listed in any `requirements*.txt` under `services/` (verified by grep across all four service requirement files), so the `import keyring` inside `_load_key_from_keyring` always raises `ImportError` and the function always returns `None`. That leaves `CREDENTIAL_ENCRYPTION_KEY`, which `.env.example` ships **blank** and `docker-compose.yml` passes through unchanged (`${CREDENTIAL_ENCRYPTION_KEY:-}`). Net effect out of the box: no key resolves, the store stays fail-closed, and `POST /auth/credentials` returns 503 — **the auth-scraping / credential feature does not function until an operator explicitly sets `CREDENTIAL_ENCRYPTION_KEY`.** To enable it: generate a key with `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"` and set `CREDENTIAL_ENCRYPTION_KEY` in `.env` (see the comment next to the var in `.env.example`). Whether to ship a working credential path by default is a product decision reserved for the user — do not add `keyring` to requirements or invent a fallback key to route around it.
- special operating rules (credential scope): every credential carries a `CredentialScope(domain, include_subdomains)` recorded AT SUBMISSION TIME — the scraper's live/dead-hop decision asks `scope.covers(host)`, never "same host as the origin". The parent domain is only ever what the submitter named; nothing derives a parent from a host, because "same registrable domain" is not computable without a public-suffix list (this repo carries none and must not add one — without it `co.uk` and `s3.amazonaws.com` read as registrable domains and every tenant of them collapses into one scope). `include_subdomains` is an EXPLICIT per-credential opt-in, defaults to **False**, and the HTTP surface (`POST /auth/credentials`) sends only a domain string — so every credential submitted through the API today gets the exact-host scope; wiring the flag through `CredentialsRequest`/the backend proxy is a follow-up owned by `main.py`/`routes.py`, and until it lands the flag is reachable only via `AuthQueue.provide_credentials(..., include_subdomains=True)`. "Exact host" means the store's OWN host key: `_extract_domain` strips a leading `www.` when storing and when retrieving, so `example.com` and `www.example.com` are already one credential in both directions, and `canonical_credential_host` makes `covers()` agree with that lookup instead of contradicting it — this is what unbreaks the ordinary `example.com -> www.example.com` canonical redirect, and it hands the credential to no host the store would not already have served it to. Subdomain matching compares on a LABEL BOUNDARY (`.` + domain): a bare `endswith` suffix test matches `evil-example.com` against `example.com` and is the specific mistake to never reintroduce. `include_subdomains` on a single-label domain or an IP literal raises `ValueError` (a coarse guard, deliberately NOT a public-suffix check). A credential stored with **no** scope (`StoredCredentials.scope is None`, i.e. written before scopes existed) is read as the strictest rule, exact host — unknown scope must always degrade toward less credential reach, never more; `store()` itself always records the default scope, and `_default_scope` returns None only when the domain cannot be canonicalized at all.
- special operating rules (hazard — read before enabling credentials): enabling the credential store by setting `CREDENTIAL_ENCRYPTION_KEY` activates the auth-scraping path (`_scrape_basic_auth` / `_scrape_cookie_auth` in `scraper/engine.py`), which is only safe once the cross-host redirect credential leak (finding C7 — a credentialed `httpx.AsyncClient` is reused by `_safe_httpx_request` to follow redirects without checking whether the redirect target host still matches the credentialed host) is fixed. C7 is fixed in this branch (a concurrent change in this same worktree, not this doc-only task). Before this branch, enabling credentials also exposed them to arbitrary redirect targets. **Do not treat "C7 is fixed in this branch" as verified fact from this card alone — it was authored by a different concurrent task; independently confirm the C7 fix actually landed before relying on this wording.**
- special operating rules (future hazard — guard before adding the `keyring` dependency): if `keyring` is ever added to `services/browser-engine/requirements.txt` to activate the OS-keyring branch, a `keyrings.alt` install (or any environment that defaults to its `PlaintextKeyring` backend) will silently persist the Fernet key in **cleartext** on disk, defeating the point of using a keyring at all. Whoever adds the dependency must pin/verify a secure backend (Secret Service / macOS Keychain / Windows Credential Locker) is actually selected at runtime — not merely that `keyring` is importable — before relying on `_load_key_from_keyring`.
- special operating rules (detection): bot-challenge / anti-scraping interstitials (Cloudflare "Just a moment..." / `cf-mitigated: challenge`, PerimeterX `px-captcha` "access denied", generic 403 "verify you are a human") are NOT credential walls — `AuthDetector` classifies them `requires_auth=False`, `auth_type="bot_challenge"`, `blocked=True`, `block_reason=<engine>` so they never enter the credential queue (WI0-B6). A bare 401/403 with no challenge markers still counts as an auth wall. The httpx scrape path re-checks 401/403 responses against the full body before enqueuing.
- current stubs/placeholders: auth callback failure handling is intentionally tolerant.
- irrelevant or incomplete code to remove/rework: none known.
- docs that must stay aligned: Browser Engine card and scraping docs.
- local validation commands/checks: `make test-browser`; focused files `tests/unit/test_auth_detector.py`, `tests/unit/test_credential_store.py`, `tests/unit/test_credential_domain_scope.py` (the last two are not in the `make test-browser` list — run them explicitly when touching `queue.py`).
