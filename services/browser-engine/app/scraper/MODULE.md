# Browser Scraper Submodule Card

- purpose: page fetching, content extraction orchestration, robots compliance, and browser lifecycle.
- product/module functionality: HTTP scrape, browser scrape, authenticated scrape, batch scrape, callback-aware scraping, resource cleanup.
- scope boundaries: owns scraper behavior; request/task API state belongs in Browser Engine routes.
- connected modules/submodules: Browser auth, extraction, Backend ingest API.
- allowed change types: resource lifecycle fixes, extraction behavior, robots policy, callback accounting, focused tests.
- special operating rules: do not reintroduce shared scraper races; `_get_browser()` must remain concurrency-safe and `close()` must stop Playwright even if browser close fails; outbound targets must pass the shared scrape URL policy. Credentials are per-REQUEST, never per-CLIENT: `httpx.AsyncClient(auth=...)` and a bare-domain client cookie jar are applied to every request unconditionally, and `_safe_httpx_request` follows up to 10 redirects across arbitrary hosts on ONE client, so a client-level credential is served to whatever host a redirect names. `_scrape_basic_auth`/`_scrape_cookie_auth` therefore pass `auth=`/`cookies=` to `_safe_httpx_get`, which attaches them (cookies folded into exactly ONE `Cookie` header by `_headers_with_cookies`, which removes any case-variant `cookie` key the caller supplied first — header names are case-insensitive, so a second dict key becomes a second `Cookie` header line, invalid under RFC 6265 and read by servers as one garbage cookie name) only while the hop stays on the origin the request STARTED at, and drops them permanently on the first crossing — never re-armed if the chain returns, since re-arming lets whoever controls the middle hop choose which authenticated request on the credential origin gets made and captured. A different host, a different port, or an `https` -> `http` downgrade is a crossing; an `http` -> `https` upgrade of an otherwise identical origin is not. The same rule governs caller-supplied headers, which is how ambient browser-session cookies forwarded by `_safe_browser_route_handler` are covered — and it is an **ALLOWLIST (`CROSS_ORIGIN_HEADER_ALLOWLIST`), never a denylist**. Removing the two named credential headers closed two instances and left the class open: `_safe_browser_route_handler` forwards a page's headers verbatim, so `X-Api-Key`, `X-Csrf-Token`, `X-Auth-*` and every vendor token header rode a cross-host redirect untouched while `Authorization`/`Cookie` were correctly absent, and that variant needs no shared IP — any cross-host redirect suffices. Once a hop has left the credential origin the caller's headers are reduced to `accept`, `accept-encoding`, `accept-language`, `user-agent`; anything added to that set must be something an anonymous client sends to every host on the internet. `Referer` is handled separately by `_referer_scoped_headers` because it is the one caller header that NAMES A DIFFERENT HOST than the one it is sent to: a page on `https://intranet.example/secret-page` fetching a subresource from a third party sends the full secret URL (path and query, tokens included) on hop 1, which is a LIVE hop for that fetch, so the cross-origin rule never fires. It is therefore reduced to origin-only whenever the target origin differs (matching browsers' `strict-origin-when-cross-origin`), dropped entirely on an `https` -> `http` downgrade, and kept in full same-origin. **Nothing rendered into a header may contain CR, LF, or NUL**: httpx does not validate header values, so a stored cookie value of `"v\r\nX-Injected: yes"` was emitted as the literal raw tuple `(b'Cookie', b'session=v\r\nX-Injected: yes')` — a second header line. `_reject_header_injection` validates every name and value at the single wire choke point (`_request_kwargs_for_target`), and `_cookie_header` re-checks per cookie so the error can name WHICH cookie; the whole request is REFUSED rather than the offending cookie dropped, because dropping returns the logged-OUT page as an authenticated success (the silent degradation this module already had to fix once) while CR/LF/NUL in a cookie value is never legitimate — RFC 6265 excludes CTLs from cookie-value. Error text names the field, never the value. The Basic-auth path needs no equivalent check: `httpx.BasicAuth` base64-encodes the credential. That per-request rule is only half the guarantee: **`_safe_httpx_request` also clears the client's own jar (`client.cookies.clear()`) on EVERY hop**, and that line is load-bearing. `resolve_scrape_targets` rewrites each hop to a vetted IP literal, so a jar entry is keyed on the ADDRESS and cannot tell two hostnames apart whenever they share a CDN edge, load balancer, reverse proxy, or host; and `http.cookiejar.add_cookie_header` injects jar cookies only when the request carries no `Cookie` header — precisely the hop the scoping rule strips. Without the clear, a `Set-Cookie` from the credential origin rides across the crossing (including the ambient browser-session cookie on the `_safe_browser_route_handler` path), and on an `origin -> attacker -> origin` chain the attacker's `Set-Cookie` is delivered BACK to the credential origin, which is the request-forgery primitive the no-re-arm rule exists to prevent. Cleared on every hop rather than only on a crossing because a jar that cannot scope has nothing to contribute on any hop; the accepted cost is that a mid-chain server-set cookie is not carried forward on a same-origin redirect (no flow depends on it — stored cookies are re-attached per live hop, and the browser path builds a fresh client per intercepted request while Playwright keeps its own jar). The host comparison is deliberately STRICT, so the very common `example.com -> www.example.com` canonical redirect DOES drop the credential: the store holds a bare `{name: value}` dict with no domain/path/Secure metadata, so nothing in it says the cookie was meant for `www`, and relaxing to the registrable domain would need a public-suffix list and would broadcast the cookie to every sibling subdomain. Because that returns the logged-OUT page, the drop must never be silent: `CredentialHopTrace` records it and `_authenticated_result` writes `metadata["credential_scope_drop"]` (hosts only — a redirect target's path/query can carry tokens) and logs `scrape.credentials_dropped_on_redirect` at WARNING. Do not weaken the per-hop `validate_scrape_url` re-validation or the redirect cap. Covered by `tests/unit/test_scraper_redirect_credentials.py`. `ScrapeResult.auth_used` is set `True` ONLY in the three credential-store branches (`_scrape_basic_auth`, `_scrape_cookie_auth`, `_scrape_form_auth`) AND, on the two httpx ones, only when the credentials actually survived to the hop that produced the captured body — a chain that left the credential origin reports `auth_used=False`, because the captured bytes came from an unauthenticated request and a false positive here mislabels public content under the plan's "authenticated capture ⇒ local embeddings" gate. The unknown-auth-type fallback to plain httpx stays `False`. It rides capture → backend ledger → `/index` document metadata (decision-37 hook). KNOWN GAP: ambient auth (cookies already in a Playwright/browser context, session reuse, auth-wall pages queued as `auth_required`) is invisible today, so `auth_used=False` there is an under-report — do not treat `False` as proof no credentials were involved.
- current stubs/placeholders: callback exceptions are intentionally best-effort but must be recorded in result metadata until a stronger contract is added; `auth_used` under-reports ambient/session auth (see special rules); the credential store has no per-cookie domain/path scope, which is why the redirect rule has to be all-or-nothing per origin — give the store real scope metadata and the strict-vs-registrable-domain question becomes answerable instead of guessed; backend's `URL_LIST_METADATA_FIELDS` whitelist does not carry `credential_scope_drop`, so a drop is visible in the ledger, export, and log but not in the `GET /api/v1/urls/{session}` projection; `_safe_browser_route_handler` passes no `CredentialHopTrace` (it fulfils a Playwright route and produces no `ScrapeResult`), so a forwarded-header drop there is enforced but not reported — per-subresource logging would be noise, and the right home for it is a page-level capture record; a POST BODY still rides a 307/308 cross-host redirect (`current_kwargs["content"]` is only stripped on 303 and on 301/302 method rewrites), so a form-login body containing a password can reach an attacker-named host even though every credential HEADER is now gone — headers were the mandated scope, and dropping or refusing the body is a separate behavior change with its own break risk.
