# AI Providers Submodule Card

- purpose: concrete AI provider adapters for cloud, local, and subscription CLI runtimes.
- product/module functionality: OpenRouter/OpenAI/Anthropic/DeepSeek/Gemini/Ollama adapters plus Claude Code, Codex CLI, Codex ACP, and Gemini CLI local CLI adapters.
- scope boundaries: owns adapter-specific request execution; shared provider selection belongs in AI Core.
- connected modules/submodules: AI Core, Shared Config, Ops Tooling host-AI mode.
- allowed change types: provider API fixes, command construction, environment isolation, availability checks, tests.
- special operating rules: never pass app/cloud secrets into local CLI subprocesses; keep Codex CLI read-only by default and reject untrusted scraped context unless explicitly overridden; keep Codex ACP deny-all default. **`gemini_cli` is the SUBSCRIPTION route and `gemini` is the metered one — do not let them meet.** `GEMINI_API_KEY`/`GOOGLE_API_KEY` are deliberately absent from `ENV_ALLOWLIST`, so the CLI subprocess physically cannot bill the API instead of spending the user's plan; adding either would breach the no-secrets rule above *and* silently move the cost model. **`--version` is NOT a sufficient availability check for `gemini_cli`, and this is measured, not theoretical**: with no credentials on disk, gemini-cli 0.54.0 exits 0 on `--version` and then blocks FOREVER on "Opening authentication page in your browser … [Y/n]" — reproduced 2026-08-06 with stdin closed and under `setsid` (no controlling terminal), surviving `timeout` and needing SIGKILL. `GeminiCliLLMProvider._availability_preflight` therefore also requires `~/.gemini/oauth_creds.json` (`GEMINI_DIR`/`OAUTH_FILE` read out of the installed bundle, not guessed). That check is a NECESSARY condition, not proof of a live session — an expired token still passes it and fails at call time — and it is a deliberate departure from this repo's "call the endpoint" rule, because here calling the endpoint IS the hazard: one logged-out probe costs an unbounded hang and one logged-in probe spends subscription quota on every availability check. `gemini_cli` also refuses untrusted scraped context by default, for the same reason `codex_cli` does: it has no tool-free mode, and its most restrictive documented approval mode (`plan`) still allows `read_file`, `google_web_search` and `web_fetch` (read from the CLI's own bundled `policies/read-only.toml`). `--approval-mode` is clamped to `{plan, default}` so no env var can hand it `yolo`. Its prompt envelope travels in **argv** (`-p <text>`), not stdin — stdin stays DEVNULL because the login prompt ignores EOF — so the argv byte limit is enforced in-process (`max_prompt_bytes`) rather than surfacing as `OSError` E2BIG. **`antigravity` is not a provider and must not become one**: `/usr/bin/antigravity` is an Electron GUI IDE with no headless mode; it opens a window and never returns.
- current stubs/placeholders: stock Docker image documents CLI providers as unavailable unless host-AI/custom image supplies binaries. **`gemini_cli` has never been executed end-to-end.** The CLI is installed on the development host (0.54.0) but not authenticated, so every hermetic test drives a fake subprocess and the one live test (`test_gemini_cli_generates_against_the_real_subscription`, `requires_provider_credentials`) SKIPS rather than passes. Treat the adapter's flags and JSON parsing as designed-from-the-shipped-implementation, not verified: run `gemini` once interactively to log in, then rerun that test.
- irrelevant or incomplete code to remove/rework: `agent_cli.py` is large; split by base class and provider subclasses later with no behavior change.
- docs that must stay aligned: AI Engine card, `docs/AI_CONFIG.md`, `.env.example`, `docker-compose.yml`.
- local validation commands/checks: `make test-ai`; focused file `tests/unit/test_subscription_cli_providers.py`; `make test-security` (SEC-46/47 cover the gemini_cli subprocess) when touching adapter argv, env, or the untrusted-context gate.
